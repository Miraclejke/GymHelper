# План реализации ЛР7 для проекта GymHelper

Дата: `2026-04-08`

## 1. Что считать ЛР7 именно для этого проекта

В методичке ЛР7 много внимания уделено внешним провайдерам аутентификации вроде `SuperTokens`, `Firebase Auth` и `Auth0`. Для проекта `GymHelper` это не лучший путь, потому что:

- у проекта уже есть рабочая backend-аутентификация через `express-session`;
- основной интерфейс уже связан именно с этим backend;
- в проекте уже есть роли `USER` и `ADMIN`;
- цель сейчас не усложнить архитектуру, а логично продолжить ЛР1-ЛР6.

Поэтому для `GymHelper` ЛР7 стоит трактовать так:

- оставить текущую `session-based auth`;
- улучшить хранение и смену пароля;
- добавить настоящую backend-авторизацию по ролям;
- сделать один понятный `admin`-сценарий;
- минимально доработать React UI под роли;
- показать это в Swagger и тестах.

Итог: ЛР7 для этого проекта должна быть не интеграцией внешнего identity provider, а развитием уже существующего модуля `auth` до полноценной аутентификации и авторизации.

## 2. Стартовая точка проекта перед ЛР7

На момент начала ЛР7 в проекте уже есть:

- `UserRole` в `prisma/schema.prisma` со значениями `USER` и `ADMIN`;
- поле `role` в модели `User`;
- `AuthService`, `AuthController`, `SessionAuthGuard`;
- endpoint'ы `GET /api/auth/me`, `POST /api/auth/login`, `POST /api/auth/register`, `POST /api/auth/logout`;
- сессия через cookie `gymhelper.sid`;
- React `AuthContext`;
- `ProtectedRoute` с поддержкой `allowedRoles`;
- тестовый администратор в `prisma/seed.js`: `admin@gymhelper.local / admin123`.

Также важно, что сейчас пароль хранится как `sha256`-хэш:

- в `src/auth/auth.service.ts`;
- в `prisma/seed.js`.

Это значит, что для ЛР7 база уже готова, и основная работа будет не в Prisma-схеме, а в backend-логике, Swagger, тестах и небольшой доработке frontend.

## 3. Адаптация методички под архитектуру GymHelper

### 3.1. Что берем из методички

Из ЛР7 в проект обязательно стоит взять:

- аутентификацию;
- авторизацию;
- разграничение ролей `user` и `admin`;
- защиту endpoint'ов через guard'ы;
- управление своей учетной записью;
- отражение защиты в Swagger;
- проверку сценариев через тесты.

### 3.2. Что адаптируем

Для `GymHelper` разумно адаптировать методичку так:

- внешний auth-провайдер не подключаем;
- `JWT` не вводим, потому что текущая архитектура уже построена на cookie-session;
- dynamic module для `auth` не делаем обязательным минимумом;
- backend-редирект на `/login` через middleware не делаем для REST API.

Почему можно не делать backend-редирект:

- основной UI у проекта это `React SPA`, а не серверные страницы;
- API должен возвращать `401 Unauthorized`, если сессии нет;
- перенаправление на `/login` уже делает frontend через `ProtectedRoute`.

То есть в вашем проекте корректная адаптация выглядит так:

- backend отвечает `401` или `403`;
- React решает, куда перенаправить пользователя;
- роли реально проверяются на сервере.

### 3.3. Что не включать в минимальный объем

Чтобы не перегрузить проект, в ЛР7 лучше не включать:

- `OAuth 2.0`;
- `Auth0`, `SuperTokens`, `Firebase Auth`;
- social login;
- email verification;
- reset password по email;
- отдельный identity microservice;
- `JWT + refresh token`;
- сложные ACL/permissions по каждой сущности;
- большую админ-панель.

Для учебного проекта это лишнее.

## 4. Рекомендуемый минимальный объем ЛР7

### 4.1. Усиление хранения пароля

Сейчас пароль хэшируется через `sha256`, что для учебного проекта уже работает, но для ЛР7 это лучше улучшить.

Рекомендуемое решение:

- заменить `sha256` на `scrypt` из `node:crypto`.

Почему именно `scrypt`:

- это встроенный инструмент Node.js;
- не нужно ставить лишнюю зависимость;
- он заметно лучше подходит для хранения паролей, чем обычный быстрый хэш;
- для учебного проекта это понятный и достаточно простой вариант.

Допустимы два пути миграции:

1. Самый простой: поменять хэширование и пересоздать тестовые данные через `seed`.
2. Чуть лучше, но сложнее: временно поддержать старый `sha256` и после успешного логина перехэшировать пароль в новый формат.

Для вашего уровня и учебного проекта я рекомендую путь `1`.

### 4.2. Управление своей учетной записью

Минимум для ЛР7:

- `PATCH /api/auth/profile` для изменения имени;
- `PATCH /api/auth/password` для изменения пароля текущего пользователя.

Эти два метода хорошо закрывают требование лабораторной про управление аккаунтом и при этом не усложняют архитектуру.

### 4.3. Backend-авторизация по ролям

Нужно добавить:

- декоратор `@Roles(...)`;
- `RolesGuard`;
- backend-проверку роли пользователя.

Важно:

- роли должны проверяться именно на сервере;
- frontend-проверка без backend-защиты не считается настоящей авторизацией.

### 4.4. Один понятный admin-only сценарий

Самый логичный минимальный admin-блок:

- `GET /api/admin/users` - список пользователей;
- `PATCH /api/admin/users/:id/role` - смена роли пользователя.

Этого достаточно, чтобы показать:

- `user` не имеет доступа;
- `admin` имеет доступ;
- роли реально влияют на API и UI.

### 4.5. Минимальная доработка frontend

На frontend уже есть почти все нужное:

- `AuthContext`;
- `ProtectedRoute`;
- `allowedRoles`.

Поэтому достаточно:

- добавить страницу `AdminUsersPage`;
- добавить маршрут `/admin/users`;
- защитить маршрут через `allowedRoles={['admin']}`;
- добавить ссылку в меню только для администратора.

Страницу профиля можно сделать, но это уже следующий приоритет после backend.

## 5. Конкретная адаптация требований методички

### 5.1. Guard'ы

Это обязательная часть. Здесь методичка полностью подходит вашему проекту.

Минимальная реализация:

- оставить `SessionAuthGuard` как guard для проверки сессии;
- добавить отдельный `RolesGuard` для ролей;
- новые admin-endpoint'ы защитить связкой `SessionAuthGuard + RolesGuard`.

### 5.2. Middleware из методички

В методичке предлагается middleware для переадресации на страницу входа.

Для `GymHelper` это можно адаптировать так:

- для REST API middleware-редирект не нужен;
- API возвращает `401`;
- React сам переводит пользователя на `/login`.

Если на защите спросят, почему нет backend-редиректа, ответ простой:

- проект не является классическим серверным MVC-приложением;
- основной интерфейс это SPA;
- для SPA корректный паттерн это `401` на API и redirect в клиентском роутинге.

### 5.3. Dynamic module

Методичка предлагает динамический модуль конфигурации `auth`.

Для вашего проекта это можно считать необязательной частью, потому что:

- сессия уже конфигурируется в `src/app.setup.ts`;
- секрет и cookie-настройки уже берутся из окружения;
- новый функционал ЛР7 можно реализовать без перестройки модуля `AuthModule`.

Если преподаватель будет требовать строгое соответствие этому пункту, это можно добавить позже как отдельное улучшение, но в минимальный и понятный план я бы это не включал.

### 5.4. CORS

В методичке отдельно упоминается настройка CORS для auth-провайдера.

Для `GymHelper` это не обязательный блок ЛР7, потому что:

- в production frontend раздается самим NestJS;
- значит, приложение работает в одном origin;
- cookie-session уже укладывается в эту схему.

CORS нужно трогать только если вы отдельно запускаете frontend и backend на разных портах во время разработки.

## 6. Что именно реализовать на backend

### 6.1. AuthService

В `AuthService` нужно:

- заменить текущее хэширование пароля;
- выделить `hashPassword(...)` и `verifyPassword(...)`;
- добавить `updateProfile(...)`;
- добавить `changePassword(...)`;
- оставить текущую структуру сервиса простой и понятной.

### 6.2. Новые DTO

Нужны DTO:

- `src/auth/dto/update-profile.dto.ts`
- `src/auth/dto/change-password.dto.ts`
- `src/admin/dto/update-user-role.dto.ts`

При желании можно добавить response DTO:

- `src/admin/dto/admin-user.response.dto.ts`

### 6.3. Roles infrastructure

Нужны файлы:

- `src/auth/roles.decorator.ts`
- `src/auth/roles.guard.ts`

Логика `RolesGuard`:

1. взять `userId` из сессии;
2. загрузить пользователя из БД;
3. получить требуемые роли из `@Roles(...)`;
4. сравнить текущую роль пользователя с требуемой;
5. если роль не подходит, вернуть `403 Forbidden`.

Лучше читать роль из БД, а не только из сессии. Тогда смена роли админом начинает действовать сразу.

### 6.4. AdminModule

Рекомендуемая структура:

```text
src/admin/
  admin.module.ts
  admin.controller.ts
  admin.service.ts
  dto/
    update-user-role.dto.ts
    admin-user.response.dto.ts
```

Что должно быть внутри:

- получение списка пользователей;
- смена роли пользователя;
- защита через `SessionAuthGuard` и `RolesGuard`.

Опционально:

- запрет на понижение последнего администратора;
- запрет на смену роли самому себе.

Эти ограничения полезны, но не обязательны для минимального варианта ЛР7.

### 6.5. Prisma и seed

Скорее всего миграция Prisma не понадобится, потому что:

- поле `role` уже есть;
- `passwordHash` уже есть;
- новый способ хранения пароля можно сохранить в то же строковое поле.

На практике нужно будет обновить:

- `prisma/seed.js`

Что именно:

- заменить `sha256` на новый способ хэширования;
- сохранить тестового администратора;
- при необходимости пересоздать тестовые данные.

## 7. Что именно реализовать на frontend

Минимум изменений:

- `frontend/src/App.tsx` - новый маршрут `/admin/users`;
- `frontend/src/components/layout/AppShell.tsx` - ссылка на admin-раздел только для `admin`;
- `frontend/src/api/authApi.ts` - методы обновления профиля и пароля;
- `frontend/src/api/types.ts` - типы для новых запросов;
- `frontend/src/pages/AdminUsersPage.tsx` - страница пользователей;
- при желании `frontend/src/api/adminApi.ts`.

Логика должна остаться такой же, как и в остальном проекте:

- получить данные;
- локально отредактировать;
- нажать кнопку сохранения;
- отправить HTTP-запрос.

Это важно, потому что frontend у вас уже построен по такому паттерну, и ЛР7 не должна его ломать.

## 8. Swagger, GraphQL и тесты

### 8.1. Swagger

Нужно:

- задокументировать новые endpoint'ы;
- сохранить `ApiCookieAuth('session')` на защищенных маршрутах;
- добавить `401` и `403` ответы там, где это нужно;
- включить admin-модуль в Swagger, если он будет отдельным модулем.

### 8.2. GraphQL

Так как основной frontend работает через `REST`, GraphQL не стоит включать в обязательный минимум ЛР7.

Базовый вариант ЛР7 можно полностью закрыть через `REST`.

Если останется время, можно добавить:

- `adminUsers` query;
- `changeUserRole` mutation;
- `GqlRolesGuard`.

Но это уже расширение, а не обязательный минимум.

### 8.3. Тесты

Минимально нужно покрыть:

1. `401`, если запрос идет без сессии;
2. `403`, если обычный пользователь идет в admin API;
3. успешный доступ администратора к `GET /api/admin/users`;
4. успешную смену роли администратором;
5. успешное изменение имени пользователя;
6. успешную смену пароля;
7. отсутствие регрессий в старых сценариях логина и базовых доменных модулях.

## 11. Критерий готовности ЛР7

ЛР7 можно считать выполненной, если:

- регистрация, логин и логаут продолжают работать;
- пароль больше не хранится как простой быстрый `sha256`;
- у пользователя есть роль `user` или `admin`;
- backend запрещает обычному пользователю доступ к admin API;
- у пользователя есть действия для управления своей учетной записью;
- есть хотя бы один admin-only сценарий;
- frontend показывает различие прав по ролям;
- Swagger отражает защищенные endpoint'ы;
- e2e-тесты подтверждают сценарии `401` и `403`;
- старые модули `plan`, `workout`, `nutrition`, `rest`, `dashboard` после этого не ломаются.

## 12. Рекомендуемая версия ЛР7 для защиты

Если делать ЛР7 в самом разумном и простом варианте, итог должен быть таким:

- свой `session-based auth` остается;
- внешний auth-провайдер не используется;
- пароль хранится безопаснее;
- есть `RolesGuard`;
- есть один `AdminModule`;
- есть `PATCH /api/auth/profile`;
- есть `PATCH /api/auth/password`;
- есть страница `/admin/users`;
- есть Swagger-документация;
- есть e2e-проверки.

Это решение:

- соответствует смыслу ЛР7;
- хорошо согласуется с вашей архитектурой `React + NestJS + Prisma`;
- не ломает ЛР1-ЛР6;
- достаточно простое для учебной реализации и защиты.
