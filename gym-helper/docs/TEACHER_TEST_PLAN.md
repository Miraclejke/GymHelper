# План Тестирования Проекта GymHelper Перед Преподавателем

## 1. Назначение документа

Этот файл нужен как готовый сценарий показа проекта перед преподавателем.

Цель:
- пройти все `ЛР1`-`ЛР7` по порядку;
- показать не только код, но и рабочий результат;
- не тратить время на импровизацию во время демонстрации;
- заранее понимать, какой шаг что подтверждает.

Документ рассчитан на текущую реализацию проекта:
- основной UI: `React SPA`;
- учебный серверный UI: `Handlebars`;
- backend: `NestJS + Prisma + PostgreSQL`;
- интерфейсы: `REST`, `Swagger`, `GraphQL`, `SSE`.

## 2. Рекомендуемый Формат Демонстрации

Оптимальный режим показа:
- основной показ вести через браузер;
- при необходимости подтверждать отдельные пункты через `Swagger`, `GraphiQL`, `curl.exe` или DevTools;
- проект запускать локально или на `Render`, но использовать один и тот же сценарий.

Рекомендуемая длительность:
- короткий показ: `15-20 минут`;
- полный показ с пояснениями: `25-35 минут`.

## 3. Что Подготовить Заранее

### 3.1. Среда

Перед демонстрацией должно быть готово:
- заполнен `.env`;

- база данных подключена;

- SPA открывается с того же домена, что и backend.

## 5.4. ЛР4. REST API И OpenAPI

### Цель показа

Подтвердить, что:
- в проекте есть полноценный `REST API`;
- используется DTO-валидация;
- подключен `Swagger`;
- коллекции поддерживают пагинацию.

### Что показать

1. Открыть `/api/docs`
2. Открыть `/api/docs-json`
3. Показать группы endpoint'ов:
   - `auth`
   - `admin`
   - `plan`
   - `workouts`
   - `nutrition`
   - `rest`
   - `dashboard`
4. Через Swagger или `curl.exe` показать:
   - `401` без логина на защищенном endpoint
   - успешную регистрацию или login
   - ошибку валидации `400`
   - пагинацию `GET /api/workouts?page=1&limit=1`

### Примеры команд

Проверка `401`:

```powershell
curl.exe -i http://localhost:3000/api/plan/mon
```

Проверка валидации:

```powershell
curl.exe -i ^
  -H "Content-Type: application/json" ^
  -d "{\"name\":\"\",\"email\":\"bad\",\"password\":\"123\"}" ^
  http://localhost:3000/api/auth/register
```

Проверка пагинации:

```powershell
curl.exe -i ^
  -b .\cookies.txt ^
  "http://localhost:3000/api/workouts?page=1&limit=1"
```

### Что проговорить

- валидация включена глобально через `ValidationPipe`;
- ошибки приводятся к единому формату;
- Swagger генерируется из backend-кода;
- пагинация дополняется `Link` и `X-Total-Count`.

### Ожидаемый результат

- Swagger UI открывается;
- неавторизованный пользователь получает `401`;
- неверный payload дает `400`;
- paginated endpoints возвращают корректные заголовки.

## 5.5. ЛР5. GraphQL

### Цель показа

Подтвердить, что:
- в проекте есть `GraphQL`-слой;
- схема создается в `code-first` режиме;
- реализованы queries и mutations;
- запросы идут к тем же backend-сервисам.

### Что показать

1. Открыть `/graphql`
2. Показать, что GraphiQL доступен
3. Выполнить query `me`
4. Выполнить query `weeklyPlan`
5. Выполнить mutation `savePlanDay` или `saveWorkoutDay`
6. Выполнить query `dashboardSummary`
7. При желании открыть `src/schema.gql`

### Рекомендуемый минимальный набор запросов

Получение текущего пользователя:

```graphql
query {
  me {
    id
    email
    role
  }
}
```

План на неделю:

```graphql
query {
  weeklyPlan {
    mon {
      name
      note
    }
  }
}
```

Сохранение плана:

```graphql
mutation {
  savePlanDay(
    weekday: MON
    input: {
      exercises: [
        { name: "GraphQL Bench", note: "4x8" }
      ]
    }
  ) {
    name
    note
  }
}
```

### Что проговорить

- GraphQL в проекте дополнительный, а не основной способ доступа;
- resolvers используют те же сервисы, что и REST;
- схема генерируется автоматически;
- включено ограничение сложности запроса.

### Ожидаемый результат

- GraphiQL работает;
- query и mutation отрабатывают;
- данные из GraphQL совпадают с backend-состоянием.

## 5.6. ЛР6. Возможности NestJS Как BFF

### Цель показа

Подтвердить, что:
- backend добавляет служебную логику вокруг данных;
- измеряется время выполнения;
- есть клиентский и серверный кэш;
- реализованы `ETag` и `304 Not Modified`.

### Что показать

1. Открыть `/lab1`
2. Показать server/client elapsed time на странице
3. Через DevTools или `curl.exe` показать `X-Elapsed-Time` на REST-запросе
4. Проверить `ETag` и `Cache-Control` на suggestions endpoint
5. Повторить запрос с `If-None-Match`
6. Показать, что после изменения workout/nutrition/rest дашборд пересчитывается заново

### Пример для `ETag`

Первый запрос:

```powershell
curl.exe -i ^
  -b .\cookies.txt ^
  http://localhost:3000/api/plan/suggestions
```

Повторный запрос:

```powershell
curl.exe -i ^
  -b .\cookies.txt ^
  -H "If-None-Match: <etag-из-первого-ответа>" ^
  http://localhost:3000/api/plan/suggestions
```

### Что важно проговорить

- в проекте реализованы timing interceptors/plugins;
- suggestions endpoint'ы умеют отдавать `ETag`;
- summary кэшируется и инвалидируется после изменения данных;
- `S3/Object Storage` в учебной реализации сознательно не используется.

### Ожидаемый результат

- в ответах виден `X-Elapsed-Time`;
- suggestions возвращают `ETag` и `Cache-Control`;
- повторный запрос по `ETag` дает `304`;
- dashboard summary обновляется после изменения данных.

### Цель показа

### Что показать

2. Показать, что после регистрации пользователь авторизован
3. Открыть `/profile`
4. Изменить имя

6. Выйти
7. Войти уже с новым паролем
8. Попробовать открыть `/admin/users` под обычным пользователем
9. Войти под `admin@gymhelper.local`
10. Открыть `/admin/users`
11. Показать список пользователей
12. Изменить роль обычному пользователю

### Дополнительная REST-проверка

Под обычным пользователем:

```powershell
curl.exe -i ^
  -b .\cookies.txt ^
  http://localhost:3000/api/admin/users
```

Ожидается:
- `403 Forbidden`

### Что проговорить

- используется `express-session`;
- пароли хранятся не в открытом виде, а через `scrypt`;
- backend сам проверяет доступ к admin-endpoint'ам;
- frontend дополнительно ограничивает доступ на уровне маршрутов.

### Ожидаемый результат

- регистрация, login и logout работают;
- профиль и пароль обновляются;
- обычный пользователь не проходит в admin;
- администратор проходит в admin и может менять роли.

## 8. Что Не Входит В Текущий Объем

Сознательно не демонстрируются как реализованные части:
- внешний auth provider;
- `S3/Object Storage`;
- загрузка файлов;
- GraphQL subscriptions;
- `nutrition`, `rest` и `admin` через GraphQL.

Это не пропуски по ошибке, а осознанная адаптация проекта под текущую учебную архитектуру.
