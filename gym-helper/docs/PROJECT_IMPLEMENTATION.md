# Описание Проекта GymHelper И Его Реализации

## 1. Что Это За Проект

`GymHelper` — учебный full-stack проект, который объединяет материалы `ЛР1`-`ЛР7` в одну цельную систему.

Смысл проекта:
- хранить недельный план тренировок;
- фиксировать выполненные тренировки по датам;
- хранить питание по датам;
- учитывать сон и восстановление;
- показывать агрегированную статистику на дашборде;
- поддерживать аутентификацию, роли и административный сценарий.

Проект не сделан как набор отдельных лабораторных.  
Наоборот, каждая лабораторная работа встроена в одну общую архитектуру и реализует отдельный слой реального приложения.

## 2. Основная Идея Реализации

В проекте есть два пользовательских слоя:

1. Основной интерфейс  
   `React SPA` из папки `frontend/`.

2. Учебный серверный интерфейс  
   `Handlebars`-страницы из папки `views/`.

Это значит, что:
- основной пользователь работает через `React`;
- backend построен на `NestJS`;
- данные хранятся в `PostgreSQL`;
- доступ к данным идет через `Prisma`;
- поверх бизнес-логики реализованы `REST`, `Swagger`, `GraphQL`, `SSE`, `cache`, `session auth`.

То есть проект показывает не отдельные разрозненные технологии, а их совместную работу внутри одной кодовой базы.

## 3. Какие Технологии Используются

### Backend

- `NestJS 11`
- `Prisma 7`
- `PostgreSQL`
- `express-session`
- `Swagger / OpenAPI`
- `GraphQL code-first`
- `Server-Sent Events`

### Frontend

- `React 18`
- `React Router`
- `Vite`
- `fetch` через общий HTTP-слой

### Инфраструктура

- `Render` для деплоя backend
- `Render PostgreSQL` для базы данных

## 4. Общая Архитектура Проекта

Структура проекта:

- `src/` — весь backend-код
- `frontend/` — клиентское React-приложение
- `views/` — серверные шаблоны Handlebars
- `public/` — собранный frontend
- `prisma/` — схема, миграции и seed
- `test/` — unit и e2e тесты
- `docs/` — проектная документация

Схема взаимодействия:

1. Пользователь открывает `React SPA`
2. `React` отправляет запросы в backend
3. `NestJS` обрабатывает запросы через контроллеры, guards и сервисы
4. Сервисы работают с БД через `Prisma`
5. Для dashboard дополнительно используется `SSE`
6. Для альтернативного API-доступа поверх той же логики добавлен `GraphQL`

## 5. Реализация Проекта По Лабораторным Работам

## 5.1. ЛР1. Деплой На Render И Шаблонизация

### Что было реализовано

В рамках `ЛР1` проект был подготовлен к развертыванию как полноценное backend-приложение на `Render`.

Также была реализована шаблонизация страниц:
- подключен `Handlebars`;
- сделан общий `layout`;
- выделены `partials`;
- созданы учебные страницы `/lab1` и `/lab1/exercises`.

### Как это реализовано

Backend запускается через:
- `src/main.ts`
- `src/app.module.ts`
- `src/app.setup.ts`

Маршруты серверных страниц и SPA fallback находятся в:
- `src/app.controller.ts`

Шаблоны расположены в:
- `views/layouts/main.hbs`
- `views/partials/*`
- `views/lab1-home.hbs`
- `views/lab1-exercises.hbs`

### Что важно в этой лабораторной

Проект показывает, что одно приложение на `NestJS` умеет:
- отдавать `React SPA` как статику;
- рендерить серверные страницы;
- обслуживать API.

### Что используется из Render

Для `Render` используется обычный web service, в котором:
- backend стартует как Node.js приложение;
- frontend предварительно собирается в `public/`;
- приложение работает на `PORT`, который задается платформой.

## 5.2. ЛР2. Создание Базы Данных На Render И Доменной Модели

### Что было реализовано

В `ЛР2` была создана доменная модель проекта и подключена реляционная БД.

В качестве БД используется `PostgreSQL`, а доступ к ней реализован через `Prisma`.

### Как это реализовано

Основная схема описана в:
- `prisma/schema.prisma`

Миграции находятся в:
- `prisma/migrations/`

Начальное заполнение базы реализовано в:
- `prisma/seed.js`

Подключение к БД в NestJS выполнено через:
- `src/prisma/prisma.service.ts`
- `src/prisma/prisma.module.ts`

### Основные сущности домена

- `User`
- `PlanDay`
- `PlanExercise`
- `WorkoutDay`
- `WorkoutExercise`
- `WorkoutSet`
- `NutritionDay`
- `MealEntry`
- `RestDay`

### Как используется Render PostgreSQL

В проекте база данных создается как отдельный `PostgreSQL service` на `Render`.

Приложение получает строку подключения через `DATABASE_URL`.

На практике используются два сценария:
- внутри Render backend подключается к своей базе через URL из окружения;
- локально можно подключиться к той же базе через `External Database URL`, если нужно проверить данные или отладить работу.

## 5.3. ЛР3. Доменная Модель И Бизнес-Логика

### Что было реализовано

В `ЛР3` проект был разделен на модули предметной области.

Основные доменные модули:
- `auth`
- `plan`
- `workout`
- `nutrition`
- `rest`
- `dashboard`

### Как устроена бизнес-логика

Каждый модуль включает:
- `controller` для входных точек;
- `service` для основной логики;
- `dto` для структуры данных;
- при необходимости дополнительные типы и вспомогательные функции.

Например:
- `PlanService` работает с недельным планом;
- `WorkoutService` сохраняет тренировки по датам;
- `NutritionService` работает с питанием;
- `RestService` работает с восстановлением;
- `DashboardService` считает агрегированную статистику.

### Как данные проходят через систему

Сценарий работы следующий:

1. frontend отправляет запрос;
2. controller принимает DTO;
3. service нормализует данные и проверяет бизнес-условия;
4. service сохраняет или читает данные через `Prisma`;
5. controller возвращает результат в frontend.

### SSE

Для обновления dashboard в реальном времени добавлен `SSE`.

Это реализовано через:
- `src/dashboard/dashboard.controller.ts`
- `src/dashboard/dashboard-events.service.ts`

Когда пользователь меняет тренировку, питание или отдых:
- backend публикует событие;
- dashboard на клиенте получает сообщение через `EventSource`;
- summary обновляется без ручной перезагрузки страницы.

## 5.4. ЛР4. REST API И Swagger

### Что было реализовано

В `ЛР4` поверх модулей был построен полноценный `REST API`.

Для проекта реализованы endpoint'ы по основным доменам:
- auth
- admin
- plan
- workouts
- nutrition
- rest
- dashboard

### Как это сделано

REST-контроллеры находятся в:
- `src/auth/auth.controller.ts`
- `src/admin/admin.controller.ts`
- `src/plan/plan.controller.ts`
- `src/workout/workout.controller.ts`
- `src/nutrition/nutrition.controller.ts`
- `src/rest/rest.controller.ts`
- `src/dashboard/dashboard.controller.ts`

### Валидация

Глобальная валидация включена через:
- `ValidationPipe` в `src/app.setup.ts`

Это дает:
- проверку структуры входных данных;
- удаление лишних полей;
- автоматическую трансформацию примитивов;
- единый отказ при неверном payload.

### Формат ошибок

Общий формат ошибок задается через:
- `src/common/filters/http-exception.filter.ts`

Это означает, что frontend и внешние клиенты получают предсказуемый JSON с ошибкой.

### Swagger

Swagger подключен в:
- `src/app.setup.ts`

Точки входа:
- `/api/docs`
- `/api/docs-json`

Таким образом, проект показывает не только наличие API, но и документирование этого API в формате `OpenAPI`.

### Пагинация

Для коллекций реализована пагинация через:
- `src/common/dto/pagination-query.dto.ts`
- `src/common/pagination.util.ts`

В ответах используются:
- `X-Total-Count`
- `Link`

## 5.5. ЛР5. GraphQL

### Что было реализовано

В `ЛР5` в проект был добавлен `GraphQL` как дополнительный способ доступа к данным.

Это не отдельная логика и не параллельное приложение.  
`GraphQL` работает поверх уже существующих сервисов.

### Как это реализовано

GraphQL-модуль расположен в:
- `src/graphql/graphql.module.ts`

Используется режим:
- `code-first`

Resolvers реализованы для:
- `auth`
- `plan`
- `workout`
- `dashboard`

Основные файлы:
- `src/graphql/auth/*`
- `src/graphql/plan/*`
- `src/graphql/workout/*`
- `src/graphql/dashboard/*`

### Что это показывает

Проект демонстрирует:
- генерацию схемы из TypeScript-кода;
- queries и mutations;
- интеграцию `GraphQL` с session-auth;
- использование тех же сервисов, что и в REST.

### Дополнительные возможности

Также в GraphQL-слое есть:
- ограничение сложности запроса;
- отдельный timing plugin;
- доступ к GraphiQL на `/graphql`.

## 5.6. ЛР6. NestJS Как BFF

### Что понимается под BFF в этом проекте

В проекте backend не просто хранит данные, а выполняет BFF-задачи:
- измеряет время обработки запросов;
- возвращает полезные HTTP-заголовки;
- кэширует часть ответов;
- управляет live-обновлениями;
- подстраивается под потребности клиента.

### Что реализовано

#### Измерение времени обработки

Для HTTP используется:
- `src/common/interceptors/request-timing.interceptor.ts`

Для GraphQL используется:
- `src/graphql/plugins/request-timing.plugin.ts`

Результат:
- в ответах появляется `X-Elapsed-Time`;
- на страницах `/lab1` показывается server/client elapsed time.

#### HTTP cache

Для suggestions endpoint'ов используется:
- `ETag`
- `Cache-Control`

Реализация:
- `src/common/interceptors/etag.interceptor.ts`

Это позволяет:
- уменьшить повторную передачу одинаковых данных;
- показать `304 Not Modified`.

#### Server-side cache

Для `dashboard summary` подключен `CacheModule`.

Основной код:
- `src/dashboard/dashboard.module.ts`
- `src/dashboard/dashboard.service.ts`

После изменения `workout`, `nutrition` или `rest` кэш summary инвалидируется вручную.

### Что сознательно не реализовано

В исходной методичке `ЛР6` есть тема загрузки файлов и `S3/Object Storage`.

В текущем проекте эта часть сознательно не включена, потому что:
- основной домен проекта не требует хранения файлов;
- задача проекта сосредоточена на тренировках, питании, отдыхе и статистике;
- остальные BFF-возможности показываются и без файловой инфраструктуры.

## 5.7. ЛР7. Аутентификация И Авторизация

### Что было реализовано

В `ЛР7` в проект добавлены:
- регистрация;
- login/logout;
- получение текущего пользователя;
- обновление профиля;
- смена пароля;
- роли;
- административный раздел.

### Как реализована аутентификация

Используется:
- `express-session`

То есть проект работает через cookie-сессии, а не через JWT и не через внешний OAuth-провайдер.

Это сделано осознанно:
- так проще показать учебный сценарий;
- это хорошо интегрируется с `NestJS`;
- это удобно для демонстрации ролей и защищенных endpoint'ов.

Основные файлы:
- `src/auth/auth.controller.ts`
- `src/auth/auth.service.ts`
- `src/auth/session-auth.guard.ts`
- `src/auth/session.util.ts`

### Хранение паролей

Пароли не сохраняются в открытом виде.

Используется:
- `scrypt`

Логика находится в:
- `src/auth/auth.service.ts`

### Авторизация

Для ролей используются:
- `Roles` decorator
- `RolesGuard`

Файлы:
- `src/auth/roles.decorator.ts`
- `src/auth/roles.guard.ts`

Роли:
- `user`
- `admin`

### Административный сценарий

Для администратора реализован отдельный модуль:
- `src/admin/*`

Он умеет:
- читать список пользователей;
- менять роль пользователя.

На frontend есть отдельная страница:
- `/admin/users`

### Что это подтверждает

Проект показывает:
- защиту приватных маршрутов;
- защиту backend-API;
- разграничение прав по ролям;
- работу профиля и пароля внутри одного приложения.

## 6. Как Все Части Проекта Связаны Между Собой

Проект сделан не как набор изолированных лабораторных, а как связанная система:

- `Render` дает платформу для публикации backend;
- `Render PostgreSQL` хранит реальные данные;
- `Prisma` описывает домен и работает с БД;
- `NestJS` реализует контроллеры, сервисы, guards и инфраструктуру;
- `REST` используется как основной API для frontend;
- `Swagger` документирует этот API;
- `GraphQL` добавляет альтернативный способ доступа к тем же данным;
- `BFF`-механизмы делают backend удобнее для frontend;
- `session auth` и роли закрывают доступ и формируют пользовательские сценарии.

Именно в этом и состоит главная идея реализации:

каждая лабораторная работа не существует отдельно, а усиливает уже построенный проект.

## 7. Итог

`GymHelper` — это учебный проект, который показывает полный путь от простого backend-приложения до полноценной системы с:

- деплоем на `Render`;
- базой данных на `Render PostgreSQL`;
- доменной моделью на `Prisma`;
- бизнес-логикой на `NestJS`;
- `REST API` и `Swagger`;
- `GraphQL`;
- BFF-возможностями;
- аутентификацией и авторизацией.

С практической точки зрения проект демонстрирует:
- работу с реальной базой данных;
- проектирование модульного backend;
- интеграцию frontend и backend;
- работу с документацией API;
- разные способы доступа к данным;
- защиту приложения и разграничение доступа.

Таким образом, проект покрывает ключевые темы `ЛР1`-`ЛР7` и показывает их в рамках одной цельной, понятной и рабочей реализации.
