# План Реализации ЛР6 Для Проекта GymHelper

Дата: `2026-04-08`

## 1. Цель ЛР6 В Контексте Проекта

Классическая формулировка ЛР6 требует показать, как `NestJS` может работать как `BFF`-слой:

- измерять время обработки запроса через `interceptor`;
- кэшировать ответы REST API на клиенте и на сервере;
- загружать файлы в объектное хранилище.

Для проекта `GymHelper` это лучше трактовать так:

- не переписывать существующий `React` frontend;
- не ломать уже готовые `REST` и `GraphQL` части;
- добавить поверх текущего backend несколько полезных инфраструктурных возможностей;
- выбрать минимальный, но логичный объем, который легко понять и показать на защите.

То есть ЛР6 для `GymHelper` должна быть не большим рефакторингом, а **аккуратным расширением текущего NestJS backend как BFF для React-клиента**.

## 2. Что Уже Готово И Почему Это Важно

К началу ЛР6 в проекте уже есть:

- `NestJS` backend с модульной структурой;
- `React` frontend внутри папки `frontend/`;
- рабочий `REST API` для `auth`, `plan`, `workouts`, `nutrition`, `rest`, `dashboard`;
- `GraphQL` как дополнительный слой поверх части сервисов;
- `Prisma + PostgreSQL`;
- `express-session`;
- глобальная валидация и Swagger/OpenAPI;
- `SSE` для dashboard;
- e2e и unit тесты.

Это значит, что в ЛР6 не нужно заново проектировать приложение. Нужно только:

1. добавить новые `interceptor`/cache/storage механизмы;
2. встроить их в уже существующие модули;
3. выбрать одну простую файловую функцию;
4. сохранить совместимость с текущим frontend.

## 3. Адаптация ЛР6 Под GymHelper

В проекте есть важная особенность: основной интерфейс уже реализован как `React SPA`, а серверный рендеринг через `Handlebars` остался только для учебных страниц из ЛР1:

- `/lab1`
- `/lab1/exercises`

Поэтому требования ЛР6 разумно адаптировать так:

- для `REST API` и `GraphQL` возвращать время обработки в заголовке `X-Elapsed-Time`;
- для шаблонов `Handlebars` показывать серверное и клиентское время именно на `lab1`-страницах;
- не переводить React-страницы на SSR только ради ЛР6.

Такой подход полностью соответствует сути работы и не ломает архитектуру проекта.

## 4. Минимальный Объем ЛР6

Чтобы реализация оставалась простой и понятной, предлагаю такой минимум.

### 4.1. Измерение Времени Ответа

Сделать один общий `RequestTimingInterceptor`, который:

- измеряет длительность обработки запроса;
- пишет время в лог;
- для `REST` и `GraphQL` добавляет заголовок `X-Elapsed-Time`;
- для `Handlebars`-маршрутов добавляет поле `serverElapsedMs` в view model.

### 4.2. Клиентский HTTP-Кэш

В минимальном варианте включить `ETag + Cache-Control` только для безопасных `GET`-endpoint'ов:

- `GET /api/plan/suggestions`
- `GET /api/workouts/suggestions`

Почему именно они:

- это простые `GET`-запросы без тела;
- ответы небольшие и стабильные;
- их легко объяснить;
- на них удобно показать `304 Not Modified`.

Если останется время, можно дополнительно распространить эту логику на:

- `GET /api/dashboard/summary`

Но это уже не обязательный минимум.

### 4.3. Серверный In-Memory Кэш

Серверный кэш лучше всего сделать для:

- `dashboard summary`

Почему именно `dashboard`:

- это главный экран приложения;
- summary агрегирует данные сразу из нескольких сущностей;
- по нему хорошо видно практический смысл кэширования;
- достаточно маленького `TTL`, например `10-15 секунд`.

### 4.4. Загрузка Файлов

Так как в проекте пока нет файловой функциональности, самый простой и понятный вариант:

- добавить загрузку **аватара пользователя**

Почему это хороший выбор:

- затрагивается только одна сущность `User`;
- не нужно переделывать тренировку, питание и сложные вложенные структуры;
- файл можно хранить отдельно, а в БД сохранить только `avatarUrl`;
- при желании потом легко показать аватар в шапке приложения.

## 5. Что Лучше Не Делать В ЛР6

Чтобы не перегружать проект, в основной объем ЛР6 **не стоит включать**:

- кэширование `GraphQL`-ответов;
- `Redis` или другой внешний кэш вместо in-memory;
- сложную инвалидизацию кэша по событиям;
- presigned URL и отдельную файловую микросервисную архитектуру;
- загрузку файлов сразу в несколько доменов;
- перевод React frontend на SSR;
- полноценный профиль пользователя с отдельным большим модулем настроек.

Для учебной работы это лишнее.

## 6. Пошаговый План Реализации

### Шаг 1. Подключить Зависимости

Для ЛР6 понадобятся:

```bash
npm i @nestjs/cache-manager cache-manager @aws-sdk/client-s3
npm i -D @types/multer
```

Этого достаточно для:

- server-side cache через `CacheModule`;
- загрузки файлов в `S3`-совместимое хранилище;
- типизации `multipart/form-data` в TypeScript.

## Шаг 2. Реализовать Interceptor Времени Ответа

Создать, например:

- `src/common/interceptors/request-timing.interceptor.ts`

Логика interceptor:

1. сохранить время начала обработки;
2. дождаться результата через `next.handle()`;
3. вычислить длительность в миллисекундах;
4. записать ее в лог;
5. вернуть клиенту:
   - в `X-Elapsed-Time` для `REST` и `GraphQL`;
   - в поле `serverElapsedMs` для view model шаблонов.

Подключить interceptor глобально:

- через `APP_INTERCEPTOR` в `AppModule`
- или через `app.useGlobalInterceptors(...)` в `app.setup.ts`

Для проекта `GymHelper` лучше использовать один глобальный interceptor, чтобы он сразу работал для:

- `/api/*`
- `/graphql`
- `/lab1`
- `/lab1/exercises`

### Шаг 3. Закрыть Требование С Шаблонами

Так как основной UI у проекта не серверный, демонстрацию времени на странице лучше сделать только на старых `Handlebars`-маршрутах.

Планируемые изменения:

- добавить вывод `serverElapsedMs` в один из `hbs` partial;
- добавить небольшой клиентский скрипт в `views/partials/shared-assets.hbs`, который замеряет клиентское время через `performance.now()`;
- вывести рядом два значения:
  - серверное время;
  - клиентское время.

Удобнее всего показывать это в:

- `views/partials/session-info.hbs`

Так требование ЛР будет закрыто без вмешательства в React SPA.

### Шаг 4. Реализовать ETag Для Выбранных REST GET

Создать отдельный interceptor, например:

- `src/common/interceptors/etag.interceptor.ts`

Его задача:

1. работать только для `GET`;
2. пропускать `SSE`, `204`, бинарные ответы и все, что не подходит для JSON;
3. сериализовать ответ;
4. считать `ETag` через хэш;
5. сравнить с `If-None-Match`;
6. если тег совпал, вернуть `304 Not Modified`;
7. если нет, выставить `ETag` в заголовке.

В минимальном варианте этот interceptor лучше повесить только на:

- `GET /api/plan/suggestions`
- `GET /api/workouts/suggestions`

Это проще, чем пытаться сразу кэшировать все GET-методы.

### Шаг 5. Добавить Cache-Control Для Клиентского Кэша

На те же endpoint'ы выставить заголовок:

```text
Cache-Control: private, max-age=3600
```

Почему `private`:

- запросы выполняются в авторизованной пользовательской сессии;
- так безопаснее для учебного проекта.

На практике это можно сделать просто через:

- `@Header('Cache-Control', 'private, max-age=3600')`

Важная идея здесь такая:

- на стороне React не нужно писать сложную собственную логику кэширования;
- роль "клиентского кэша" будет выполнять стандартный HTTP-кэш браузера.

Это самый простой и правильный учебный вариант.

### Шаг 6. Подключить Server-Side Cache Для Dashboard

Добавить `CacheModule` в `DashboardModule`.

Рекомендуемая конфигурация:

- `ttl: 10-15 секунд`

Дальше в `DashboardService` использовать `CACHE_MANAGER` и хранить результат по ключу:

```text
dashboard:summary:{userId}
```

Логика должна быть такой:

1. при запросе summary сначала проверить кэш;
2. если значение есть, вернуть его из памяти;
3. если значения нет, посчитать summary обычным способом;
4. сохранить результат в кэш;
5. вернуть его клиенту.

Для учебной работы **не нужно** делать ручную инвалидизацию при каждом `saveDay`.
Достаточно короткого `TTL`.

### Шаг 7. Создать Инфраструктурный StorageModule

Для загрузки файлов лучше сделать отдельный модуль по аналогии с `PrismaModule`.

Примерная структура:

```text
src/storage/
  storage.module.ts
  storage.service.ts
  storage.types.ts
```

Что должен делать `StorageService`:

- создавать `S3Client`;
- загружать файл в бакет;
- генерировать итоговый публичный URL;
- возвращать минимальную информацию об объекте.

Нужные env-переменные:

- `S3_ENDPOINT`
- `S3_REGION`
- `S3_BUCKET`
- `S3_ACCESS_KEY_ID`
- `S3_SECRET_ACCESS_KEY`
- `S3_PUBLIC_BASE_URL`

Для `Yandex Object Storage` использовать `AWS SDK for JavaScript` и `S3Client`.

### Шаг 8. Добавить Простую Файловую Функцию: Avatar Upload

Самый простой вариант для проекта:

- расширить `User` в Prisma полем `avatarUrl String?`

После этого:

1. добавить endpoint загрузки файла;
2. после загрузки обновлять `avatarUrl` у пользователя;
3. возвращать обновленного пользователя.

Самый удобный endpoint:

- `POST /api/auth/avatar`

Почему в `auth`, а не в отдельном большом `users`-модуле:

- уже есть работа с текущим пользователем;
- уже есть `GET /api/auth/me`;
- меньше новых сущностей и файлов;
- проще объяснить на защите.

### Шаг 9. Подключить Multipart Upload В Контроллере

В `AuthController` для endpoint загрузки использовать:

- `@UseInterceptors(FileInterceptor('file'))`

Добавить валидацию файла:

- только изображения;
- ограничение размера, например `2 МБ`.

Для простого и понятного решения этого достаточно.

В Swagger нужно отдельно описать `multipart/form-data`, чтобы загрузку можно было проверить прямо через `/api/docs`.

### Шаг 10. Согласовать Типы AuthUser

После добавления аватара нужно расширить:

- `src/common/api.types.ts`
- `src/auth/dto/auth-user.response.dto.ts`
- `frontend/src/store/types.ts`

Добавить туда:

- `avatarUrl?: string`

Тогда `GET /api/auth/me`, `login`, `register` и `upload avatar` будут возвращать единый формат пользователя.

### Шаг 11. Минимальная Интеграция С Frontend

Для ЛР6 основной минимум можно закрыть даже без отдельной frontend-страницы загрузки.

Самый простой вариант:

- backend endpoint загрузки проверять через Swagger;
- `avatarUrl` вернуть в `GET /api/auth/me`;
- при желании как маленькое улучшение показать аватар в:
  - `frontend/src/components/layout/AppShell.tsx`

То есть frontend-часть для ЛР6 лучше сделать **минимальной и необязательной**.

## 8. Как Проверять Готовность ЛР6

### 8.1. Автоматическая Проверка

Из корня проекта выполнить:

```bash
npm run test -- --runInBand
npm run test:e2e
npm run build
```

Ожидаемый результат:

- проект собирается;
- существующие сценарии не ломаются;
- новый код не ломает REST, GraphQL и React-интеграцию.

### 8.2. Ручная Проверка Interceptor Времени

Проверить:

1. `GET /api/auth/me`
2. `GET /api/dashboard/summary`
3. `POST /graphql`
4. `/lab1`

Ожидаемый результат:

- у REST и GraphQL ответов есть `X-Elapsed-Time`;
- на `lab1`-странице отображаются серверное и клиентское время;
- в логах видно измерение длительности запроса.

### 8.3. Ручная Проверка Клиентского Кэша

Проверить:

1. выполнить `GET /api/plan/suggestions`;
2. повторить тот же запрос;
3. посмотреть заголовки `Cache-Control` и `ETag`;
4. убедиться, что при повторной проверке можно получить `304 Not Modified`.

Если хочется показать эффект нагляднее, это удобно делать через вкладку `Network` в DevTools браузера.

### 8.4. Ручная Проверка Server-Side Cache

Проверить:

1. несколько раз подряд вызвать `GET /api/dashboard/summary`;
2. посмотреть, что часть запросов обслуживается быстрее;
3. при желании добавить временный лог `cache hit / cache miss`.

Дополнительно, если хочется продемонстрировать эффект красивее:

```bash
hey -n 20 -c 5 http://localhost:3000/api/dashboard/summary
```

Но для `hey` нужно помнить про авторизованную cookie-сессию, поэтому этот шаг можно оставить как необязательный.

### 8.5. Ручная Проверка Upload

Проверить через Swagger:

1. авторизоваться;
2. вызвать `POST /api/auth/avatar`;
3. загрузить изображение;
4. затем вызвать `GET /api/auth/me`.

Ожидаемый результат:

- файл загружается в объектное хранилище;
- в ответе пользователя появляется `avatarUrl`;
- файл доступен по URL из бакета.

## 9. Критерий Готовности ЛР6

ЛР6 можно считать выполненной, если:

- в проекте есть interceptor измерения времени ответа;
- `X-Elapsed-Time` возвращается для `REST` и `GraphQL`;
- на `lab1`-страницах видно серверное и клиентское время;
- хотя бы часть REST GET-методов поддерживает `ETag` и `Cache-Control`;
- `dashboard summary` кэшируется на сервере через `CacheModule`;
- есть отдельный storage-модуль для работы с `S3`-совместимым хранилищем;
- можно загрузить хотя бы один тип файла в бакет;
- информация о загруженном файле связывается с предметной сущностью проекта;
- текущий `REST API`, `GraphQL` и React frontend после этого продолжают работать.

## 10. Итоговая Рекомендация

Для проекта `GymHelper` и текущего уровня сложности лучший вариант ЛР6 такой:

- сделать один глобальный interceptor времени;
- показать клиентский кэш на `suggestions` endpoint'ах;
- сделать server-side cache только для `dashboard summary`;
- реализовать одну простую файловую функцию через `avatar upload`;
- использовать `lab1`-страницы только как учебную площадку для шаблонной части задания.

Это решение:

- достаточно простое;
- хорошо соответствует текущей архитектуре проекта;
- не требует переписывать frontend;
- легко объясняется на защите;
- закрывает все основные требования ЛР6 без лишнего усложнения.
